## 1. 项目背景与目标

### 1.1 背景

宿舍是典型的"多设备、多状态、强关联"空间：照明、空调、窗帘、加湿器、插排、门锁各自独立，学生每天要重复完成"熄灯—合帘—锁门""回寝—开灯—开帘"这类动作组合。真实痛点不是"缺一个遥控器"，而是：

1. 设备之间没有联动，人的作息状态（在寝 / 离开 / 就寝）无法自动传导到设备；
2. 环境变化（升温、变干、光照变化）需要人主动发现并处理；
3. 即使做了联动，多条规则同时命中时缺少**冲突仲裁**，容易出现"刚关又被开"的抖动。

### 1.2 目标

构建一款 HarmonyOS 应用，把宿舍抽象为"设备 + 属性"的统一数据模型，通过可配置的**条件—动作规则**驱动设备状态，并用**Mock 环境模拟器**持续制造状态变化，使"无人操作也会自动执行"成为可观察、可验证的真实现象；同时保证所有业务数据（设备、规则、日志）在关闭应用后不丢失。

### 1.3 范围

- 范围内：单机应用；设备为 Mock 数据（不接入真实硬件）；规则由用户可视化配置；日志本地留存。
- 范围外：账号体系、云端同步、真实 IoT 协议接入、多用户权限。

## 2. 用户与使用场景

### 2.1 用户角色

| 角色 | 说明 | 主要诉求 |
| --- | --- | --- |
| 宿舍住户（主用户） | 24 栋 305 的住宿学生 | 少操作、环境舒适、离开后不浪费电 |
| 评阅者（旁观者） | 教师 / 同学 | 能快速看清"规则是否真的在跑" |

### 2.2 核心场景

1. **就寝**：人数归零、光照降到阈值以下 → 自动熄灯、合帘、反锁，并写入日志。
2. **回寝补光**：有人进入且光照不足 → 自动开主灯到 80% 亮度。
3. **高温降温**：温度 ≥ 28℃ → 空调开机并设定 24℃；温度 ≥ 32℃ 时"极端环境自保"以更高优先级接管。
4. **干燥加湿**：湿度 < 40% → 加湿器开机、档位调到 2。
5. **一键场景**：手动点「就寝 / 起床 / 离家 / 回寝」，一次性写入一组设备状态（与自动规则形成对照）。
6. **回溯**：在日志页查看"谁在什么时间、因为哪条规则、把哪个设备改成了什么"。

## 3. 功能需求

| 编号 | 功能 | 说明 | 输入 / 输出 | 优先级 |
| --- | --- | --- | --- | --- |
| FR-01 | 环境快照 | 展示温度、湿度、光照、在寝人数四项指标，数值随模拟器演化 | 输入：模拟节拍；输出：四项数值与状态文案 | 高 |
| FR-02 | 设备控制 | 设备卡片支持开关；详情页支持滑杆/步进精细调节 | 输入：用户手势；输出：设备属性变更 + 手动日志 | 高 |
| FR-03 | 快捷场景 | 四个预置场景，一键写入一组动作 | 输入：场景 id；输出：变更数量提示 + 场景日志 | 中 |
| FR-04 | 规则管理 | 规则的增、删、改、启停；可视化编辑条件与动作 | 输入：表单；输出：规则对象 + 校验错误提示 | 高 |
| FR-05 | 规则执行 | 每 3 秒评估：条件组（ALL/ANY）→ 优先级排序 → 冷却过滤 → 冲突消解 → 写动作 | 输入：设备状态 + 规则集 + 时间；输出：执行计划 | 高 |
| FR-06 | 执行日志 | 记录自动 / 手动 / 场景 / 冲突 / 系统五类事件，支持筛选与清空 | 输入：事件；输出：倒序日志列表 | 高 |
| FR-07 | 数据持久化 | 设备、规则、日志写入本地；冷启动恢复；切后台强制落盘 | 输入：业务快照；输出：下次启动的初始状态 | 高 |
| FR-08 | 设置 | 环境模拟开关、立即评估、立即保存、清空日志、恢复默认、关于信息 | 输入：用户操作；输出：状态与统计刷新 | 中 |

### 3.1 关键业务规则（FR-05 细化）

1. **条件求值**：`compare(op, 实际值, 阈值)`，浮点比较带 0.05 容差；设备或属性缺失时判为"不满足"，不抛异常。
2. **条件组**：`ALL` 要求全部成立；`ANY` 任一成立；空条件组视为不成立（防止误触发）。
3. **优先级**：规则按 `priority` 降序、`id` 升序排序，保证同一状态下结果确定。
4. **冷却**：距上次触发不足 `cooldownSec` 的规则被跳过，并记入 `blocked`（原因可读）。
5. **冲突消解**：同一设备的同一属性被多条规则争用时，高优先级生效，低优先级记入 `conflicts`，日志页展示"按优先级让位"。
6. **只读保护**：传感器不可写，命中此类动作时拦截并记录原因。

## 4. 非功能需求

| 类别 | 要求 |

### 5.2 数据流

```
环境模拟(3s) ──► 传感器属性变化
                      │
用户操作 ─────────────┤
                      ▼
             RuleEngine.buildPlan(rules, devices, now)
                      │  matched / assignments / conflicts / blocked
                      ▼

                      └──► AppRepository.save(分片 JSON, flush)
```

## 8. 接口定义

| 接口 / 方法 | 输入参数 | 返回值 | 异常 / 边界处理 |
| --- | --- | --- | --- |
| RuleEngine.compare(op, left, right) | CompareOp, number, number | boolean | 浮点按 EPS=0.05 比较 |
| RuleEngine.ruleMatches(rule, devices) | Rule, Device[] | boolean | 空条件/停用 → false；设备缺失 → 不满足 |
| RuleEngine.buildPlan(rules, devices, now) | Rule[], Device[], number | ExecutionPlan | 冷却/只读/设备缺失 → blocked；争用 → conflicts |
| RuleEngine.validateRule(rule, devices) | Rule, Device[] | string[] | 返回全部错误；空数组表示合法 |
| HomeStore.tick() | 无 | void | 内部捕获异常，不中断节拍 |
| HomeStore.setDeviceValue(id, key, v) | string, string, number | boolean | 不存在/只读/无变化 → false |
| HomeStore.saveRule(rule) | Rule | string[] | 校验失败不落库，返回错误 |
| AppRepository.init(context) | UIAbilityContext | boolean | 初始化失败时 ready=false，页面提示"存储未就绪" |
| AppRepository.load() | 无 | SnapshotBundle \| undefined | 分片缺失/解析失败 → undefined，回退默认数据 |
| AppRepository.save(bundle) | SnapshotBundle | boolean | 分片写入 + 清理旧分片 + flush |

## 9. 存储方式

1. **介质**：`@kit.ArkData` 的 `preferences`，文件名 `qiju_store`。
2. **格式**：整份业务快照序列化为一个 JSON 字符串（`SnapshotBundle`）。
3. **分片**：preferences 单值上限 8KB，故按 2000 字符切片，写入 `snap_0 … snap_n`，并用 `snap_count` 记录片数；写入时删除上次多余分片，避免脏数据。
4. **时机**：启动 `init()` 首次写入；业务动作立即写；节拍内最多每 4 秒写一次；切后台 `onBackground` 与 `onDestroy` 强制写。
5. **恢复**：`getPreferencesSync + getSync` 同步读取，保证首帧就是恢复后的状态，不出现"先默认后跳变"。
6. **兜底**：解析异常 → 返回 undefined → 使用默认设备与预置规则，并在日志中注明"首次启动"。

## 11. 验收标准

1. 全新安装后 3 秒内能看到环境数值变化；无人操作时日志出现"自动执行"记录。
2. 新建/编辑规则后立即生效；非法配置（空名称、动作指向传感器）被拦截并提示。
3. 关闭应用（后台清理）后重新启动，设备状态、规则、日志均恢复。
4. 两条规则争用同一属性时，界面与日志都能看出"高优先级生效、低优先级让位"。
5. `hvigorw assembleHap` 编译通过；hypium 用例覆盖正常 / 边界 / 异常三类。
